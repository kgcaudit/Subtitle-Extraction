# subex 웹 — 브라우저에서 영상 자막 추출

영상 파일을 고르면 그 안의 자막을 **SRT 파일로** 뽑습니다. 자막이 그림으로 들어 있으면
브라우저 안에서 글자로 읽어 냅니다.

**영상은 이 기기 밖으로 나가지 않습니다.** 서버로 올리지 않고 브라우저 안에서만 처리합니다.
설치할 것도 없고, 안드로이드·아이폰·PC·맥 어디서든 브라우저만 있으면 됩니다.

## 쓰는 법

```bash
cd web
npm install && npm run vendor   # 문자 인식 엔진을 vendor/ 로 복사 (한 번만)
npm run serve                   # http://127.0.0.1:8080
```

### 공개된 주소

**https://kgcaudit.github.io/Subtitle-Extraction/**

이 저장소에 올릴 때마다 `.github/workflows/pages.yml` 이 자동으로 다시 배포합니다.
올릴 때 문자 인식 엔진과 언어 자료를 함께 담으므로, 공개 배포망에 기대지 않고
사이트 혼자 돌아갑니다.

직접 배포하실 때도 이 폴더를 정적 파일 그대로 올리면 끝입니다(사내 웹서버, 파일 공유 등).
**서버에서 도는 프로그램이 없습니다.**

`npm run vendor` 를 하면 인식 엔진과 언어 자료가 `vendor/` 에 들어가서 **바깥 인터넷이
막힌 사내망에서도** 그대로 동작합니다. 하지 않으면 공개 배포망에서 받아 옵니다.

## 지원 범위

| 영상 안의 자막 | 처리 | 결과 |
|---|---|---|
| **SubRip** 글자 자막 | 바로 변환 | ✅ 즉시 |
| **ASS/SSA** 글자 자막 | 스타일 태그 제거 후 변환 | ✅ 즉시 |
| **PGS** 그림 자막 (블루레이) | 그림 복원 → 문자 인식 | ✅ |
| **VobSub** 그림 자막 (DVD) | 그림 복원 → 문자 인식 | ✅ |
| **.idx + .sub 자막 파일** (영상 없이) | 그림 복원 → 문자 인식 | ✅ |
| **MP4 글자 자막** (tx3g/mov_text) | 바로 변환 | ✅ 즉시 |
| MP4 안의 WebVTT (wvtt) | 바로 변환 | ✅ 즉시 |
| DVB 자막 (방송) | — | ❌ 미지원 (목록에는 표시) |
| 화면에 새겨진 자막 (번인) | — | ❌ 범위 밖 |

컨테이너는 **MKV · WebM · MP4 · MOV** 를 읽습니다. 확장자가 아니라 파일 앞머리를 보고
가리므로 이름이 엉뚱해도 됩니다. 자막만 든 **.sup** 파일도 바로 넣을 수 있습니다.

### DVD 자막(.idx + .sub)은 두 파일을 함께

따로 뽑아 둔 DVD 자막은 늘 두 파일이 짝입니다.

- **.sub** — 자막 그림이 들어 있습니다(MPEG 프로그램 스트림).
- **.idx** — 색(팔레트)과 "몇 시 몇 분 자막이 .sub 의 몇 번째 바이트에 있는지" 표입니다.

**.sub 하나만으로는 읽을 수 없습니다.** 색도 시각도 .idx 에 있기 때문입니다.

**하나씩 차례로 고르면 됩니다.** 먼저 고른 것을 들고 있다가 짝이 오면 잇습니다.
순서는 상관없고, 한 번에 둘을 골라도 됩니다.

> 휴대폰 파일 고르기는 대개 **한 번에 하나만** 고르게 합니다. 그래서 '두 개를
> 함께 고르라' 고 하면 폰에서는 쓸 수가 없습니다. 파일 종류를 확장자가 아니라
> 앞머리 내용으로 가리는 것도 같은 이유입니다 — 폰 파일 고르기가 `.idx`/`.sub`
> 같은 낯선 확장자를 걸러 버려 아예 고를 수 없게 되는 일이 있습니다.

.idx 안에 언어가 여러 개면 언어마다 트랙 하나로 보여 줍니다.

## 인식 정확도 — 언어 설정이 크게 좌우합니다

한글 자막 400줄로 실측한 값입니다.

| 인식 언어 | 한글만 있는 자막 | 한·영 섞인 자막 |
|---|---|---|
| 한국어만 | **98.0%** | 39% ❌ 영문이 깨집니다 |
| 한국어 + 영어 | 89.7% | **100%** |

어느 한쪽이 항상 낫지 않습니다. 그래서 기본값은 **자동**입니다.

자동은 앞부분 12장을 '한국어+영어'로 읽어 보고 두 가지를 함께 봅니다.

1. 거기서 나온 **영문 낱말을 인식기가 얼마나 확신하는지** (50 이상)
2. 낱말 가운데 **영문이 얼마나 되는지** (20% 이상)

**둘 다** 맞아야 영어를 함께 씁니다. 실제로 재어 본 값입니다.

| 자료 | 영문 낱말 비율 | 확신도 | 고른 언어 |
|---|---|---|---|
| 한글 전용 (합성 자료) | 0.0% | — | 한국어만 |
| 한글 전용 (실제 DVD 자막 1,578줄) | 5.7% | 54.8 | 한국어만 |
| 한·영 혼합 (합성 자료) | 53.8% | 95.4 | 한국어+영어 |

> 처음에는 두 설정의 전체 신뢰도를 견주려 했는데, 400장에서 89.8 대 89.5 로
> 뒤집혀 못 쓸 방법이었습니다. 확신도만 보도록 바꾸니 **89.7% → 98.0%** 가
> 됐습니다. 그런데 실제 DVD 자막을 넣어 보니 그것만으로도 모자랐습니다.
> 기울어진 노래 가사가 영문으로 잘못 읽히면서 확신도가 54.8 로 어중간하게
> 높게 나와, 한글 전용 자막인데도 '한국어+영어'를 골랐습니다. 그래서 비율을
> 함께 보게 했습니다.

판단은 한쪽으로 치우쳐 둡니다. 한글 전용 자막을 '한국어+영어'로 읽으면 멀쩡한
한글 낱말이 영문으로 뭉개지지만(실측: 300줄 중 83줄, 28%), 영문이 조금 섞인
자막을 '한국어만'으로 읽으면 그 몇 낱말만 깨집니다. 그래서 **영문이 진짜로
섞여 있다는 증거가 뚜렷할 때만** 영어를 함께 씁니다.

글자 크기는 손댈 필요가 거의 없습니다. 인식기가 알아서 맞춥니다.

## 어떻게 검증했나

이 저장소의 **파이썬판이 정답지**입니다. 실제 영상으로 검증을 끝낸 구현이라,
웹판이 같은 입력에서 같은 답을 내는지를 기준으로 삼았습니다.

```bash
npm test
```

38개 시험이 있고, 대부분 **파이썬판이 낸 답과 맞춰 봅니다**.

| 시험 | 내용 |
|---|---|
| SRT 규칙 대조 | 까다로운 11가지 경우에서 파이썬판과 글자 단위로 같은지 |
| PGS 그림 해독 | 파이썬판이 해독한 그림과 **픽셀 단위로** 같은지 (.sup 파일 / MKV 안 둘 다) |
| VobSub 그림 해독 | 위와 같음 |
| MKV 글자 자막 | SubRip 이 그대로 읽히는지 |
| MP4 자막 트랙 | 트랙·언어를 찾아내고, SRT 와 시각이 파이썬판과 **밀리초까지** 같은지 |
| 파일 종류 가리기 | 앞머리만 보고 MKV·MP4·.sup 을 구분하고, 모르는 형식은 이유를 알려 주는지 |
| 자막 없는 영상 | 빈 목록과 안내 문구가 나오는지 |
| 실제 자막에 가까운 PGS | 안티에일리어싱(수십 가지 색)과 두 줄을 각각 다른 객체로 얹은 경우도 픽셀 단위로 같은지 |
| 자동 언어 선택 | 한글 전용 자막에서는 '한국어만', 한·영 혼합에서는 '한국어+영어'를 고르는지 |
| 기울기 바로 세우기 | 기울기를 제대로 재는지, 되돌린 뒤 기울기가 0이 되는지, 똑바른 그림은 손대지 않는지 |
| 글자 크기 맞춤 | 줄 높이를 제대로 재는지, 큰 글자만 줄이고 작은 글자는 그대로 두는지 |
| 줄 가르기·음표 | 줄 수만큼 갈리는지, **글꼴이 그린 진짜 ♪** 를 찾아 떼어 내는지, 글자를 음표로 잘못 보지 않는지 |
| 트랙 줄 높이 | 가운데가 빈 짧은 줄을 도로 붙이는지, 진짜 두 줄은 붙이지 않는지, 조각난 그림이 섞여도 줄 높이가 흔들리지 않는지 |
| .idx/.sub 짝 | 영상 없이 자막 파일 두 개만 넣어도 파이썬판과 픽셀 단위로 같은지, .idx 표를 언어별로 갈라 읽는지, **하나씩 차례로 골라도**(양쪽 순서 모두) 이어지는지 |
| **브라우저 전체 흐름** | 진짜 크로미움에서 MKV·MP4·.sup·.idx+.sub 을 넣고 끝까지 돌려, 만들어진 SRT 가 파이썬판 결과와 **바이트 단위로 같은지** |

마지막 시험이 핵심입니다. 자막을 꺼내고, 그림을 해독하고, 글자를 읽고, 다듬어
SRT 로 만드는 전 과정을 한 번에 확인합니다.

### 실제 DVD 자막으로 재어 본 값

영화 한 편 분량의 실제 한글 DVD 자막(1,578줄, 1920x1080, 7.4메가바이트)을
크로미움에서 끝까지 돌린 결과입니다.

| 단계 | 측정값 |
|---|---|
| 자막 트랙 찾기 | **5밀리초** |
| 1,578줄 꺼내고 그림 해독 | **1.2초** |
| 문자 인식 (한국어, 인식기 4개) | **24.7초** |
| 전체 | **약 30초** |

손으로 받아 적은 정답지 64줄로 잰 결과입니다.

| | 글자정확도 | 완전히 맞은 자막 | ㅈ↔ㅅ 실수 | ♪ 되살림 | 줄 앞 잡음 |
|---|---|---|---|---|---|
| 처음 | 91.53% | 39/64 | 12 | 0 | 212줄 |
| 기울기 바로 세운 뒤 | 95.26% | 39/64 | 9 | 0 | 114줄 |
| 글자 크기까지 맞춘 뒤 | 96.73% | 49/64 | **0** | 0 | 94줄 |
| 줄마다 따로 + 음표 되살림 | 99.10% | 59/64 | **0** | 231곳 | 17줄 |
| **줄 높이를 트랙에서 잰 뒤** | **99.44%** | **60/64** | **0** | **231곳** | **0줄** |

남은 것은 `고맙네`→`고압네` 처럼 글자 하나가 어긋나는 경우 네 군데뿐입니다.

그림 해독은 **파이썬판과 픽셀 하나까지 같았고**(605만 픽셀 대조, 차이 0),
1,578줄의 시각도 **모두 밀리초까지 같았습니다**. 파이썬판은 ffprobe 로 읽고
웹판은 프로그램 스트림을 직접 훑으므로, 서로 다른 길로 같은 답에 닿은 셈입니다.
글자는 **97.96%** 가 같았는데, 남은 차이는 인식 엔진이 서로 달라서(WebAssembly 대
네이티브) 생기는 것이고 웹판이 더 잘 읽은 곳도 섞여 있습니다.

처음 돌렸을 때 인식이 무너진 곳은 **기울어진 노래 가사(♪)** 였습니다.
자막 글꼴이 기울면 인식기가 거의 못 읽습니다. 합성 자료로는 밟아 볼 수 없던
부분이라, 실제 영화 자막을 넣고서야 드러났습니다.

### 기울어진 글자 바로 세우기

그래서 **글자를 먼저 바로 세우고** 읽습니다. 바로 선 글자는 세로획이 같은 열에
모이므로, 열마다 잉크량을 재면 획이 있는 열과 없는 열의 차이가 큽니다. 여러
기울기로 되돌려 보고 그 차이가 가장 큰 것을 고릅니다.

| 자막 | 바로 세우기 전 | 후 |
|---|---|---|
| 노래 가사 215줄 (기울어짐) | 한글 31.6% | **92.8%** |
| 대사 220줄 (똑바름) | 한글 97.3% | 97.3% (그대로) |

똑바른 글자에서는 기울기를 0으로 재므로 **아무것도 건드리지 않습니다.**
영화 한 편 전체로는 이렇게 달라졌습니다.

| | 전 | 후 |
|---|---|---|
| 못 읽은 자막 | 215줄 (13.6%) | **10줄 (0.6%)** |
| 전체 한글 비율 | 77.3% | **92.3%** |

```
전: .?/7/.</으 흔 을을 ////./들 / 준//_.7 8/./?7
후: 마지막 한 발을 내디딜 / 준비가 됐니?
```

기울기를 재는 데 장당 6밀리초가 더 들지만, 그림이 깨끗해진 만큼 인식이 빨라져
전체 시간은 오히려 줄었습니다(49.8초 → 48.7초).

### 글자는 클수록 좋은 게 아닙니다

그 다음으로 남은 것이 **ㅈ 을 ㅅ 으로 읽는 실수**였습니다. `자네가`→`사네가`,
`저런`→`서런`, `제 말`→`세 말` 같은 것입니다. 그림을 열어 보면 `자` 가 또렷한데도
그랬습니다. 그래서 전처리가 아니라 **넣는 크기**를 의심했습니다.

같은 자막을 원본 크기를 바꿔 가며(한 줄 25~100픽셀) 재 봤더니 분명했습니다.

| 인식기에 넣는 크기 | 글자정확도(최저) | ㅈ↔ㅅ 실수(최다) |
|---|---|---|
| 2배로 키움 (예전 기본값) | 92.10% | **14** |
| 손대지 않음 | 93.79% | 8 |
| **28픽셀로 줄임** | **96.61%** | **0** |

**키우는 것은 어느 크기에서도 손해였습니다.** 예전 기본값이 2배 확대였으니,
설정을 바꿀수록 나빠지고 있었던 셈입니다. 그래서 큰 글자만 줄이고 키우지는
않습니다. 한 줄이 40픽셀보다 작으면 줄여도 나아지지 않으므로(실측) 그냥 둡니다.

> 흐리게만 해 봐도(ㅈ↔ㅅ 8~10), 줄였다 다시 키워 봐도(2~6) 안 됐습니다.
> **작게 넣는 것 자체**가 듣는 방법이었습니다.

덤으로 그림이 작아져 인식이 **두 배 가까이 빨라졌습니다**(37.5초 → 19.9초).

### 줄마다 따로 읽습니다

자막 한 덩이를 통째로 넣으면, 인식기가 줄 배치를 제 나름대로 해석합니다.
자막은 가운데 맞춤이라 줄마다 여백이 다른데, 그 여백을 글자로 오해해 앞에
`.` 이나 `_` 를 만들어 내고 때로는 **한 줄을 통째로 흘립니다.**

```
전: . 그런 말투는 / 누구한테 배웠나?     ← 없는 점이 생김
전: 펑크에 → 평크에                    ← '팝이' 가 사라짐
```

그래서 글자 줄마다 잘라 따로 넣습니다. 잘라 낼 때는 위아래에 줄 높이의 15%를
남깁니다. 딱 붙여 자르면 인식기가 글자의 기준선을 못 잡고(실측: `English` →
`Enalish`), 너무 넉넉하면 옆 줄이 딸려 들어옵니다.

### 줄 높이는 트랙 전체에서 잽니다

`응` 이나 `요즘` 처럼 위아래로 쌓인 글자는 **가운데가 가로로 비어 있습니다.**
긴 줄에서는 옆 글자들이 그 자리를 메우지만, 글자 몇 자뿐인 짧은 줄에서는
그대로 끊깁니다. 그러면 한 줄이 두 줄로 갈려 엉뚱하게 읽힙니다.

```
전: - 왔어? / "> / 222      ← '- 응' 이 두 조각으로 끊김
후: - 왔어? / - 응
```

조각 사이 틈(12픽셀)이 줄 사이 틈(11픽셀)과 거의 같아서, **틈 크기만으로는
가릴 수 없습니다.** 대신 자막은 한 트랙 안에서 글자 크기가 일정하다는 점을
씁니다. 여러 자막에서 재어 가운데 값을 쓰면 아주 안정적입니다(실측: 자막
1,578개에서 중앙값 49픽셀, 사분위 48~49픽셀).

그 값을 기준으로 '합쳐도 한 줄 높이를 넘지 않으면 같은 줄' 로 붙이고, 너무
얇게 잡힌 띠는 글자가 잘린 것으로 보고 한 줄 크기로 넓힙니다. 쓰레기 줄이
**11줄 → 0줄** 이 됐습니다.

### 음표(♪)는 그림에서 찾아냅니다

노래 자막의 ♪ 는 **인식기가 절대 못 읽습니다.** 한국어·영어 글자 목록
(1158자 / 112자)에 ♪ 가 아예 없기 때문입니다. 실제로 영화 한 편에서 한 번도
못 읽었고, 대신 `》` `^` `_` `>` 같은 엉뚱한 글자를 내거나 그냥 흘렸습니다.

글자로는 고칠 수 없으니 **그림에서 직접 찾습니다.** 줄 맨 앞 덩어리를 ♪ 본과
견줘 봅니다. 실측으로 두 무리가 확실히 갈립니다.

| | 본과 닮은 정도 |
|---|---|
| **음표** | 0.49 ~ 0.74 |
| 한글 | -0.14 ~ 0.27 |
| 대시(`-`) | -0.09 ~ -0.03 |

찾으면 그림에서 지우고(안 지우면 인식기가 그 자리에 엉뚱한 글자를 만듭니다)
결과 앞에 ♪ 를 붙입니다. 영화 한 편에서 **231곳**을 되살렸고, 눈으로 확인한
것 중 잘못 붙인 곳은 없었습니다.

### 실제 영상으로 검증하기

가진 영상을 넣으면 웹판을 돌려 보고, 이 컴퓨터에 파이썬판이 있으면 **자동으로
대조까지** 해 줍니다.

```bash
node tools/verify.js /경로/영화.mkv            # 웹판 실행 + 파이썬판 대조
node tools/verify.js 영화.mkv --dump 5         # 해독한 그림도 5장 저장해 눈으로 확인
node tools/verify.js 영화.mkv --lang kor       # 인식 언어를 직접 지정
node tools/verify.js 영화.mkv --no-python      # 대조 없이 웹판만
node tools/verify.js 자막.idx 자막.sub         # DVD 자막은 두 파일을 함께
```

내놓는 것: 트랙 목록, 단계별 걸린 시간, SRT 파일, 그리고 파이썬판과의
**시각 일치 여부**와 **글자 일치율**, 다른 곳 다섯 군데까지.

시각이 다르면 자막을 꺼내는 쪽 문제이고, 글자만 다르면 문자 인식 차이입니다.
`--dump` 로 저장되는 그림을 보면 인식기가 무엇을 보고 읽었는지 알 수 있습니다.

기준 자료를 다시 만들려면:

```bash
python3 ../tests/make_web_fixtures.py     # 그림·영상·SRT 정답지
python3 ../tests/make_parity_golden.py    # SRT 규칙 정답지
```

## 구조

```
web/
├── index.html · styles.css        화면 (반응형, 360픽셀부터)
├── src/
│   ├── reader.js       파일을 조각내어 읽기 (필요한 구간만)
│   ├── container.js    파일 종류를 가려 알맞은 해석기로
│   ├── mkv.js          MKV/WebM 해석 — 자막 트랙만 골라 꺼낸다
│   ├── mp4.js          MP4/MOV 해석 — 표(stbl)를 엮어 자막 조각 위치를 찾는다
│   ├── pgs.js          PGS 그림 해독 (세그먼트 + 런렝스)
│   ├── vobsub.js       VobSub 그림 해독 (제어 시퀀스 + 2비트 런렝스)
│   ├── vobsubFile.js   .idx 표 읽기 + .sub(MPEG 프로그램 스트림)에서 자막 꺼내기
│   ├── source.js       고른 파일들을 정리 (.idx/.sub 을 하나씩 받아 모은다)
│   ├── extract.js      위 셋을 엮어 '시각 + 내용' 으로
│   ├── bitmapPrep.js   문자 인식 전처리 (기울기·크기 맞추기, 줄 가르기, 음표 찾기)
│   ├── ocr.js          문자 인식 (tesseract.js, 여러 개 병렬)
│   ├── postprocess.js  다듬기 (빈 줄·겹침·중복)
│   ├── srt.js          SRT 읽기/쓰기
│   └── app.js          화면 동작
├── tools/              개발 서버, 인식 엔진 복사, 실제 영상 검증(verify.js)
└── test/               위 검증들
```

## 아직 안 된 것

- **조각난 MP4(fragmented)** — 스트리밍용으로 만든 MP4 입니다. 읽으려 하면
  그렇다고 알려 줍니다.
- **DVB 자막(방송)** — 목록에는 보이지만 해독기가 없습니다.
- **화면에 새겨진 자막(번인)** — 자막 트랙이 아니라 영상 그림의 일부라 범위 밖입니다.
- 문자 인식은 한국어+영어로 맞춰 두었습니다. 다른 언어는 `vendor.js` 의 언어 목록과
  `ocr.js` 의 기본값을 바꾸면 됩니다.
