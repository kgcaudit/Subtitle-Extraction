# subex 웹 — 브라우저에서 영상 자막 추출

영상 파일을 고르면 그 안의 자막을 **SRT 파일로** 뽑습니다. 자막이 그림으로 들어 있으면
브라우저 안에서 글자로 읽어 냅니다.

**영상은 이 기기 밖으로 나가지 않습니다.** 서버로 올리지 않고 브라우저 안에서만 처리합니다.
설치할 것도 없고, 안드로이드·아이폰·PC·맥 어디서든 브라우저만 있으면 됩니다.

**바로 쓰기: https://kgcaudit.github.io/Subtitle-Extraction/**

## 지원 범위

| 영상 안의 자막 | 처리 | 결과 |
|---|---|---|
| **SubRip** 글자 자막 | 바로 변환 | ✅ 즉시 |
| **ASS/SSA** 글자 자막 | 스타일 태그 제거 후 변환 | ✅ 즉시 |
| **PGS** 그림 자막 (블루레이) | 그림 복원 → 문자 인식 | ✅ |
| **VobSub** 그림 자막 (DVD) | 그림 복원 → 문자 인식 | ✅ |
| **.idx + .sub 자막 파일** (영상 없이) | 그림 복원 → 문자 인식 | ✅ |
| **MP4 글자 자막** (tx3g/mov_text) | 바로 변환 | ✅ 즉시 |
| MP4 안의 WebVTT (wvtt) | 바로 변환 | ✅ 즉시 |
| DVB 자막 (방송) | — | ❌ 미지원 (목록에는 표시) |
| 화면에 새겨진 자막 (번인) | — | ❌ 범위 밖 |

컨테이너는 **MKV · WebM · MP4 · MOV** 를 읽습니다. 확장자가 아니라 파일 앞머리를 보고
가리므로 이름이 엉뚱해도 됩니다. 자막만 든 **.sup** 파일도 바로 넣을 수 있습니다.

### DVD 자막(.idx + .sub)은 두 파일이 짝

- **.sub** — 자막 그림이 들어 있습니다(MPEG 프로그램 스트림).
- **.idx** — 색(팔레트)과 "몇 시 몇 분 자막이 .sub 의 몇 번째 바이트에 있는지" 표입니다.

**.sub 하나만으로는 읽을 수 없습니다.** 색도 시각도 .idx 에 있기 때문입니다.
**하나씩 차례로 고르면 됩니다** — 먼저 고른 것을 들고 있다가 짝이 오면 잇습니다.
순서는 상관없고, 한 번에 둘을 골라도 됩니다.

> 휴대폰 파일 고르기는 대개 **한 번에 하나만** 고르게 합니다. 그래서 '두 개를
> 함께 고르라' 고 하면 폰에서는 쓸 수가 없습니다. 파일 종류를 확장자가 아니라
> 앞머리 내용으로 가리는 것도 같은 이유입니다 — 폰 파일 고르기가 `.idx`/`.sub`
> 같은 낯선 확장자를 걸러 버려 아예 고를 수 없게 되는 일이 있습니다.

.idx 안에 언어가 여러 개면 언어마다 트랙 하나로 보여 줍니다.

## 무슨 파일을 열었는지 화면에 남습니다

파일을 고르면 **고르는 칸 자리에 그 파일 이름과 크기**가 들어앉습니다. 예전에는
이름이 상태 글에 잠깐 스쳤다가 `자막 트랙 28개를 찾았습니다` 로 덮여 사라져서,
화면을 찍어 놓고 보면 어느 영상에서 뽑은 자막인지 알 수가 없었습니다.

DVD 자막은 `.idx` 와 `.sub` 두 파일이 짝이므로 **둘 다** 적습니다
(`sample.sub + sample.idx`). 이름이 길어도 줄이지 않고 감싸서 다 보여 줍니다 —
줄이면 정작 무슨 파일인지 알 수 없기 때문입니다.

## 미리보기는 시작 시각과 함께 보여 줍니다

뽑은 자막은 앞부분 다섯 개를 미리 보여 주는데, **자막마다 시작 시각을 앞에**
적습니다(`00:01:02.300`).

- 대사만 늘어놓으면 영상의 **어느 대목인지** 알 수 없었습니다.
- **어디까지가 자막 하나인지**도 구별되지 않았습니다 — 두 줄짜리 자막 하나가
  자막 두 개처럼 보였습니다. 이제 두 줄은 한 시각 아래 묶여 있습니다.
- 시각과 대사를 **두 칸으로 나눠** 그립니다. 글자 수로 자리를 맞추면 대사가
  접혀 내려갈 때 시각 칸 밑으로 흘러듭니다.
- 좁은 화면에서 접힐 때는 **어절 단위로** 접습니다(`word-break: keep-all`).
  한 낱말이 통째로 넘칠 때만 낱말 안에서 자릅니다.

> 화면에서는 `00:01:02.300` 처럼 **점**으로 적고, 자막 파일 안에는 SRT 규칙대로
> **쉼표**(`00:01:02,300`)로 씁니다. 값은 같고 표기만 다릅니다.

## 자막이 스물여덟 개인 파일에서 고르고 받기

블루레이 리믹스에는 자막이 스무 개, 서른 개씩 붙어 있습니다. 그중 한국어 하나만
쓰는 게 보통인데, 하나씩 눌러야 하면 폰에서는 쓸 수가 없습니다.

**고를 때**

- 자막이 **다섯 개 이하면** 처음부터 다 골라 둡니다. 그보다 많으면 **아무것도
  골라 두지 않습니다** — 스물여덟 개를 다 뽑을 사람은 거의 없고, 지우는 일이
  고르는 일보다 번거롭기 때문입니다.
- **전체 선택 / 전체 해제** 단추가 있습니다.
- 언어가 두 가지 이상이면 **언어 알약**(`KOR 2`, `ENG 1` …)이 나옵니다. 누르면
  그 언어 자막만 한꺼번에 켜지고, 다시 누르면 꺼집니다. 언어가 하나뿐이면
  보여 주지 않습니다.
- 지금 몇 개를 골랐는지(`8개 중 2개 선택`)를 늘 보여 줍니다.

**추출 단추는 화면을 따라다닙니다**

자막 28개짜리 파일에서 단추를 목록 맨 끝에 두면 작은 폰(360×640)에서 **4화면**,
아이폰 14(390×844)에서 **2.7화면**을 내려가야 닿았습니다. 그래서 `몇 개 선택 +
추출 단추 + 진행선` 을 한 막대에 모아 화면 아래에 붙여 둡니다.

- `position: fixed` 가 아니라 **`sticky`** 입니다. 제 구역 안에서만 붙어 다니므로
  자막이 서너 개여서 목록이 한 화면에 들어오면 **아무 일도 하지 않습니다** —
  예전과 똑같이 보입니다. 맨 아래까지 내리면 막대가 제자리로 돌아가 마지막
  트랙을 가리지 않습니다.
- 돌아가는 동안 막대 위쪽에 **진행선**이 그려지고 단추에 `추출 중… 3/8` 이
  적힙니다. 상태 글은 페이지 맨 위에 있어 자막이 많으면 화면 밖이라, 눌러도
  아무 일도 안 일어나는 것처럼 보였습니다.
- 다 되면 **결과로 데려다 줍니다**(움직임을 줄여 달라고 설정한 분에게는 건너뛰듯).
- 결과의 `한 번에 받기` 단추에도 같은 막대를 씁니다. 두 막대는 서로 다른 구역에
  묶여 있어 겹치지 않습니다.
- 아이폰 홈 인디케이터 여백은 따로 두지 않습니다. `viewport-fit=cover` 를 쓰지
  않으므로 iOS 가 화면 자체를 안전 영역 안으로 줄여 주고,
  `env(safe-area-inset-*)` 는 0 이 됩니다 — 넣어 봐야 아무 값도 더하지 않습니다.

> 대신 한 화면에 보이는 트랙이 **10개에서 9개로** 줄어듭니다(390×844 기준, 막대가
> 69픽셀). `sticky` 를 모르는 아주 오래된 브라우저에서는 그냥 예전 모습으로
> 보입니다 — 망가지지 않습니다.

**뽑을 때**

고른 자막은 **한꺼번에 뽑습니다.** 파일은 한 번만 지나갑니다(아래 *여러 트랙은 한
번에 꺼냅니다*). 트랙마다 따로 뽑는 길은 남아 있지 않습니다 — 하나를 골라도 같은
길로 갑니다.

**받을 때**

- 결과마다 **내려받기** 단추가 그대로 있습니다(하나만 받을 때).
- 결과에도 **전체 선택 / 전체 해제** 와 체크 상자가 있어, 골라서 **한 번에** 받을
  수 있습니다. 두 개 이상이면 **zip 하나로 묶어** 줍니다.
- 묶는 일은 바깥 라이브러리 없이 직접 합니다(`src/zip.js`, 압축하지 않는 *저장*
  방식). 자막은 작아서 압축해도 별 이득이 없고, 압축기를 하나 더 들이면 틀릴
  자리만 늘어납니다. 만든 zip 은 파이썬 `zipfile` 이 그대로 열어 보는 것으로
  확인합니다.

> **왜 굳이 zip 인가.** 브라우저에게 파일 여러 개를 연달아 내려받게 하면 '여러
> 파일 내려받기를 허용하시겠습니까' 를 묻거나 그냥 막아 버립니다. 폰에서 특히
> 그렇습니다. 하나로 묶으면 그런 일이 없습니다.
>
> **묶음 이름은 영문·숫자로만 짓습니다**(`영화이름.subtitles-3.zip`). 크로뮴은
> 내려받을 파일 이름을 시스템 로케일로 옮기지 못하면 **이름을 통째로 버리고**
> 확장자 없는 `download` 로 저장해 버립니다(로케일이 UTF-8 이 아닌 PC 에서
> 재현했습니다). 확장자를 잃으면 폰에서 zip 으로 열리지 않습니다.

## 얼마나 걸리나

실제로 끝까지 돌려 잰 값입니다(PC 크로미움, 4코어).

| 자료 | 훑어 꺼내기 | 문자 인식 | 전체 |
|---|---|---|---|
| DVD 자막 7.4MB, 1,578줄 (영화 A) | 1.2초 | 24.5초 | **약 30초** |
| DVD 자막 6.7MB, 1,661줄 (영화 B) | 1.2초 | 25.8초 | **약 32초** |
| 블루레이 자막 23.7MB, 1,593줄 (영화 C) | 10.4초 | 30.9초 | **약 47초** |
| 영상 676MB, PGS 400줄 | 4.5초 | 12.4초 | **약 21초** |

> 블루레이 자막(`.sup`)이 꺼내는 데 더 오래 걸리는 것은 그림이 압축된 형태로
> 들어 있어 **전부 풀어야 하기** 때문입니다. DVD 자막은 차례표(`.idx`)가 있어서
> 필요한 자리만 찾아 읽습니다.

### MKV 안의 자막은 색인을 따라갑니다

MKV 는 자막 조각이 영상·소리와 **뒤섞여 파일 전체에 흩어져** 있습니다. 그냥
훑으면 자막 몇십 킬로바이트를 얻으려고 영상 파일을 통째로 읽게 됩니다.

다행히 대부분의 MKV 에는 `Cues` 라는 색인이 있고, 만드는 도구들이 **자막
트랙까지** 색인해 둡니다. 그래서 자막이 있는 자리로 바로 건너뜁니다.

| 374MB 영상, 자막 1,200줄 | 파일에서 읽는 양 |
|---|---|
| 처음부터 끝까지 훑기 | 372.8MB (**99.6%**) |
| **색인 따라가기** | **3.3MB (0.9%)** |

**110배** 차이입니다. 나오는 자막은 두 방법이 바이트 하나까지 같고, 시험으로
맞춰 봅니다. 색인이 없거나 자막 트랙이 색인에 빠져 있으면 조용히 훑는 쪽으로
돌아갑니다.

### 읽는 '양' 만 줄이면 오히려 느려집니다

처음에는 자리를 하나씩 차례로 읽었습니다. 읽는 양은 125배 줄었는데 **휴대폰에서는
더 느렸습니다.** 한 번 읽을 때마다 붙는 지연이 읽는 양보다 크게 작용하기
때문입니다 — 작은 읽기를 721번 줄 세우면 지연만 쌓입니다.

| 374MB 영상, 자막 1,200줄 (한 번 읽을 때 5밀리초 지연 가정) | 걸린 시간 |
|---|---|
| 처음부터 끝까지 훑기 | 2.62초 |
| 색인을 따라가되 **하나씩 차례로** | 3.97초 ❌ 더 느리다 |
| 색인을 따라가되 **한꺼번에 8개씩** | **0.61초** |

그래서 두 가지를 함께 합니다.

- **한꺼번에 읽습니다.** 자리를 미리 다 알고 있으므로 차례로 기다릴 이유가 없습니다.
- **어느 쪽이 싼지 계산해서 고릅니다.** 둘 다 '파일을 몇 번 나눠 읽나' 로 값을
  매깁니다 — 훑기는 `파일 크기 ÷ 1MB` 번, 색인은 `자막 수 ÷ 8` 번. 작은 파일은
  몇 번만 읽으면 끝이라 훑는 쪽이 낫고, 큰 영화는 색인이 압도적입니다.

| 파일 | 자막 | 훑기 | 색인 | 고르는 쪽 |
|---|---|---|---|---|
| 374MB | 1,200줄 | 357번 | 150번 | **색인** |
| 700MB | 1,600줄 | 668번 | 200번 | **색인** |
| 83MB | 1,200줄 | 80번 | 150번 | 훑기 |
| 20MB | 1,200줄 | 20번 | 150번 | 훑기 |

색인이 이기는 쪽만 고르므로 **어느 경우에도 손해가 없습니다.**

색인을 곧이곧대로 믿지도 않습니다. 앞쪽 16자리를 먼저 읽어 보고 한 조각도 안
나오면, 나머지 수백 자리를 헛되이 읽지 말고 바로 훑는 쪽으로 넘깁니다 — 자리
계산이 다른 만듦새의 파일에서 '헛수고 + 훑기' 로 두 배 느려지는 것을 막습니다.

### 여러 트랙은 한 번에 꺼냅니다

자막 트랙을 여러 개 고르면 **파일을 한 번만 지나가며 다 담습니다.** 트랙마다 따로
읽으면 MKV 는 파일을 트랙 수만큼 반복해서 읽습니다.

| 83MB 영상, 자막 트랙 3개 | 파일에서 읽는 양 | 걸린 시간 |
|---|---|---|
| 트랙마다 따로 | 247.9MB (**299%**) | 0.56초 |
| **한 번에** | **82.6MB (100%)** | **0.16초** |

`mkvextract` 도 같은 방식입니다. 색인을 쓸 때도 트랙별 색인을 합쳐 한 번에 읽으므로
같은 이득이 있고, 여러 트랙의 자막이 같은 덩어리에 들어 있으면 머리말을 나눠 씁니다.

그림 자막은 트랙마다 수십 메가바이트라, 한 트랙을 다 쓰고 나면 **바로 놓아 줍니다.**
읽기만 한 번에 하고 해독·문자인식은 예전처럼 트랙마다 차례로 합니다.

- 자막 트랙 목록만 보는 것은 **5밀리초** 입니다(파일 앞 1메가바이트만 읽습니다).
- 문자 인식은 **글자 줄 하나에 20~25밀리초** 쯤입니다(인식기 4개 병렬).
- 글자 자막은 인식이 없으므로 훑는 시간이 전부입니다.

> **훑는 시간은 저장장치 속도가 정합니다.** 위 676메가바이트 값(4.5초)은 파일이
> 이미 메모리 캐시에 있을 때입니다. 디스크에서 실제로 읽으면 같은 파일이
> **45초** 걸렸습니다. 휴대폰이라면 저장장치 읽기 속도가 그대로 병목이 됩니다.

## 얼마나 정확한가

**실제 한글 영화 자막 세 편**(DVD 두 편 + 블루레이 한 편)으로 재었습니다. 자막을
화면에 그려 본 그림을 눈으로 읽어 정답지를 손으로 만들고, 세 편 모두 **휴대폰과
PC 에서 각각 끝까지 돌려** 따로 맞춰 봤습니다.

| | 영화 A<br>(DVD) | | 영화 B<br>(DVD) | | 영화 C<br>(블루레이) | |
|---|---|---|---|---|---|---|
| | **폰** | PC | **폰** | PC | **폰** | PC |
| 자막 | 1,578줄 | ← | 1,661줄 | ← | 1,593줄 | ← |
| 정답지 | 손으로 64줄 | ← | 손으로 60줄 | ← | 손으로 30줄 | ← |
| **글자정확도** | **99.55%** | 99.44% | **98.62%** | 98.35% | **99.75%** | **99.75%** |
| 완전히 맞은 자막 | 60/64 | 59/64 | 53/60 | 53/60 | 29/30 | 29/30 |
| ㅈ↔ㅅ 실수 | 0 | 0 | 1 | 0 | 0 | 0 |
| 한글 한 자도 없는 줄 | 0 / 2,206 | 0 / 2,518 | 3 / 2,348 | 4 / 2,349 | **2 / 2,217** | 3 / 2,217 |

영화 C 는 **실제 블루레이에서 뜬 `.sup` 자막**(한국어)입니다. 세 편 중 가장
정확했고, 틀린 한 곳(`껍데기`→`검데기`)조차 인식 모델의 글자 목록에 `껍` 이
없어서 생긴 것입니다 — **모델이 낼 수 있는 최선에 닿아 있습니다.**

> 폰에서 잰 영화 A 의 자막 수는 '빈 결과 다시 읽기' 를 넣기 전 값(1,577줄)입니다.
> 그 규칙으로 되살아난 두 줄은 정답지 64줄에 들어 있지 않아 **정확도 값은 그대로
> 유효합니다**(넣기 전과 후 모두 99.44%).

**폰이 PC보다 떨어지지 않습니다.** 세 편 모두 같거나 오히려 폰 쪽이 조금 높게
나왔는데, 정답지가 30~64줄이라 이 정도 차이(0.1~0.3%포인트)는 오차 범위입니다.
뒤집힌 곳이 서로 섞여 있습니다 — 영화 B 에서 폰은 `넌 날 미치게`를 맞혔고 PC 는
`년`으로 틀렸으며, 반대로 폰은 `오징어 조명 쇼`를 `소명`으로 틀렸습니다.

**글자 두세 개짜리 짧은 줄**은 두 엔진 모두 약하고, 어느 쪽이 약한지가 자료마다
다릅니다. 영화 B 에서는 폰이 `네` 한 줄을 흘리고 PC 가 `131` 로 읽었고, 영화 C
에서는 반대로 PC 가 `잠깐...` 을 빈 글자로 내놓아 **자막 하나를 통째로 잃었습니다**
(1,593 대 1,592). 그래서 빈 결과가 나오면 '한 낱말' 모드로 한 번 더 읽도록
고쳤습니다(아래 [3. 줄마다 따로 읽습니다](#3-줄마다-따로-읽습니다) 참고). 지금은
양쪽 다 1,593줄이고, 영화 A 도 1,577 → 1,578줄이 됐습니다.

### 영화 A — 다듬는 단계마다 얼마나 올랐나

전처리를 하나씩 붙여 가며 같은 정답지로 잰 값입니다. 정확도의 대부분이 인식기가
아니라 **넣기 전 그림을 어떻게 다듬느냐**에서 나옵니다.

| | 글자정확도 | 완전히 맞은 자막 | ㅈ↔ㅅ 실수 | ♪ 되살림 | 줄 앞 잡음 |
|---|---|---|---|---|---|
| 처음 | 91.53% | 39/64 | 12 | 0 | 212줄 |
| 기울기 바로 세운 뒤 | 95.26% | 39/64 | 9 | 0 | 114줄 |
| 글자 크기까지 맞춘 뒤 | 96.73% | 49/64 | **0** | 0 | 94줄 |
| 줄마다 따로 + 음표 되살림 | 99.10% | 59/64 | **0** | 231곳 | 17줄 |
| **줄 높이를 트랙에서 잰 뒤** | **99.55%** | **60/64** | **0** | **231곳** | **0줄** |

남은 것은 `고맙네`→`고맘네` 처럼 **글자 하나가 어긋나는 경우 네 군데**뿐입니다.

### 영화 B — 손대지 않은 자막으로 다시 재기

영화 A 에 맞춰 놓은 설정이 **다른 자막에서도 통하는지** 보려고, 아무것도 고치지
않은 채로 두 번째 영화를 넣었습니다. 글꼴·제작 도구·자막 관습이 모두 다릅니다.

- **글자정확도 98.62%**(폰) / 98.35%(PC), 60줄 중 53줄이 완전히 일치합니다.
- **ㅈ↔ㅅ 실수 0~1개** — 영화 A 에서 잡은 크기 규칙이 그대로 통했습니다.
- 자동 언어 선택이 **한국어만**을 골랐습니다(맞습니다).
- 음표를 **0곳** 되살렸는데, 이것도 맞습니다. 이 영화는 노래를 음표가 아니라
  **기울임꼴로만** 표시합니다(자막의 36%가 기울임꼴, ♪ 글리프는 아예 없음).
  글자 모양만 보고 '줄 앞 이상한 글자 = 음표' 로 고쳤다면 여기서 없는 음표를
  231개쯤 만들어 냈을 것입니다.
- 대시로 시작하는 50줄이 **한 줄도 띄어지지 않았습니다.** 이 자막의 원본 관습
  그대로입니다(아래 [7. 마무리 손질](#7-마무리-손질) 참고).

틀린 7군데는 아래와 같습니다. 두 기기가 서로 다르게 틀린 곳이 섞여 있습니다.

| 정답 | 폰 | PC |
|---|---|---|
| 내가 **쟤** 목소릴 | 내가 **재** 목소릴 | 내가 **재** 목소릴 |
| **솟**아날 구멍은 있지 | **숫**아날 구멍은 있지 | **숫**아날 구멍은 있지 |
| **넌** 날 미치게 | 넌 날 미치게 ✅ | **년** 날 미치게 |
| 오, **맙소**사 | 오, **마**사 | 오, **맘소**사 |
| **노먼** | **노머** | **너머** |
| 오징어 **조**명 쇼 | 오징어 **소**명 쇼 | 오징어 조명 쇼 ✅ |
| **네** (두 줄 자막의 첫 줄) | (줄이 통째로 빠짐) | **131** |

마지막 `네` 처럼 **글자 한두 개짜리 짧은 줄**이 가장 약합니다. 인식기가 아무것도
못 내놓거나(폰) 숫자로 읽거나(PC) 둘 중 하나인데, 트랙 전체에서 3곳입니다.
크기를 28·32·36·40픽셀로 바꿔 보고, 좌우 여백을 잘라 보고, 인식 모드를 7·8·10·13
으로 바꿔 봐도 어느 것도 고쳐지지 않았습니다. 여기서부터는 한국어 인식 모델을
자막 글꼴로 다시 학습시키는 수준의 일이 됩니다.

### 폰과 PC 는 얼마나 다른가

**자막을 꺼내고 시각을 매기는 부분은 완전히 같습니다.**

| | 영화 B (DVD) | 영화 C (블루레이) |
|---|---|---|
| 자막 수 | 폰 1,661 / PC 1,661 — **같음** | 폰 1,593 / PC 1,593 — **같음** |
| 시작·끝 시각 | **1,661줄 전부 밀리초까지 같음** | **1,593줄 전부 밀리초까지 같음** |
| 글자가 다른 자막 | 175개 (**10.5%**) | 154개 (**9.7%**) |
| 글자 일치율 | 99.87% | 99.17% |

다른 것은 문자 인식뿐이고, 인식기(tesseract.js)가 기기에 따라 다른 WebAssembly
빌드를 쓰기 때문입니다. 세 편에서 8~10.5% 의 자막이 조금씩 달랐지만 **어느 쪽이
더 정확하다고 할 수 없습니다**(위 표 참고). 흔들리는 것은 글자 하나 수준이고,
틀리는 자리가 기기마다 다를 뿐입니다.

## 글자 자막과 그림 자막을 어떻게 가르나

자막 트랙에는 규격상 **코덱 이름표**가 반드시 붙어 있습니다. 그래서 알맹이를 열어
'이게 글자인가 그림인가' 를 따질 필요가 없습니다. 이름표만 보면 확정입니다.

| MKV 안의 코덱 아이디 | 이름표 | 종류 |
|---|---|---|
| `S_HDMV/PGS` | `application/pgs` | **그림** (블루레이) |
| `S_VOBSUB` | `application/vobsub` | **그림** (DVD) |
| `S_DVBSUB` | `application/dvbsubs` | **그림** (방송 — 아직 못 읽음) |
| `S_TEXT/UTF8`, `S_TEXT/ASCII` | `application/x-subrip` | 글자 |
| `S_TEXT/ASS`, `S_TEXT/SSA` | `text/x-ssa` | 글자 |
| `S_TEXT/WEBVTT` | `text/vtt` | 글자 |

```js
export const BITMAP_MIME_TYPES = new Set([MIME.PGS, MIME.VOBSUB]);
export function isBitmap(track) { return BITMAP_MIME_TYPES.has(track.mimeType); }
```

파이썬판도 같은 방식입니다. `ffprobe` 가 알려 주는 `codec_name` 이 목록
(`hdmv_pgs_subtitle`, `dvd_subtitle`, `dvb_subtitle`, `dvb_teletext`, `xsub`)에
있으면 그림, 없으면 글자입니다.

화면에 `글자 자막 — 바로 변환됩니다` 라고 뜨는 것이 이 판정 결과입니다. 그림이면
`그림 → 문자인식` 이라고 나옵니다.

### 자막만 든 파일은 앞머리 몇 바이트로 가립니다

트랙이 아니라 **파일 자체가 자막**인 경우(`.sup`, `.idx`+`.sub`)는 확장자를 믿지
않고 파일 앞머리를 봅니다.

| 앞머리 | 무엇 |
|---|---|
| `PG` (0x50 0x47) | 블루레이 자막 → 그림 |
| `00 00 01 BA` | MPEG 프로그램 스트림 = `.sub` → 그림 (짝 `.idx` 필요) |
| `1A 45 DF A3` | MKV·WebM |
| 5~8번째가 `ftyp` | MP4·MOV |

확장자를 안 믿는 이유는 **휴대폰 파일 고르기가 `.idx`·`.sub` 같은 낯선 확장자를
걸러 버려 아예 고를 수 없게 되는 일이 있기 때문**입니다(위 [DVD 자막](#dvd-자막idx--sub은-두-파일이-짝)
참고).

## 글자 자막은 어떻게 뽑나

갈림길은 딱 한 줄입니다. 글자 자막이면 **인식기를 만들지도 않고** 빠져나갑니다.

```js
let textCues = cues;
if (cues.some((cue) => cue.image)) {      // 그림이 하나라도 있을 때만
  pool ??= await startOcr(...);           // 여기서 처음 인식기를 내려받는다
  textCues = await recognizeCues(...);
}
```

그래서 글자 자막만 뽑을 때는 **인식기(약 7MB)를 내려받지 않습니다.**

```
자막 트랙 ─ 조각 꺼내기 ─ UTF-8 로 읽기 ─ 시각 보정 ─ 마무리 손질 ─ SRT
```

1. **조각 꺼내기** — 컨테이너에서 그 트랙의 조각만 모읍니다. MKV 는 색인을 따라
   자막 자리로 바로 건너뜁니다([위](#mkv-안의-자막은-색인을-따라갑니다) 참고).
2. **글자로 읽기** — 조각의 바이트를 UTF-8 로 디코드합니다. 형식마다 조금씩
   다릅니다 — ASS/SSA 는 앞쪽의 서식 칸을 떼어 내고, MP4 글자 자막(tx3g)은
   '길이 2바이트 + 본문' 에서 본문만 꺼내며, MP4 안의 WebVTT 는 `payl` 상자를
   찾아 읽습니다.
3. **시각 보정** — 자막이 영상과 같은 시간축에 오도록 맞춥니다.
4. **마무리 손질** — 그림 자막과 **똑같은** 손질을 받습니다
   (아래 [7. 마무리 손질](#7-마무리-손질) 참고).

1,000줄에 **0.1초도 안 걸립니다.** 원본 글자를 그대로 옮기는 것이라 정확도는
100% 입니다 — 틀릴 여지가 없습니다.

> 파이썬판은 브라우저가 아니므로 ffmpeg 에게 `-c:s srt` 로 형식만 바꾸게 합니다.
> 바로 최종 파일로 쓰지 않고 한 번 읽어 들이는데, 그림 자막과 **똑같은 마무리
> 손질·인코딩 선택**을 거치게 하기 위해서입니다.

## 그림 자막을 어떻게 읽나

그림에서 글자를 읽어 내는 일은 **넣기 전에 그림을 어떻게 다듬느냐**가 거의 다
결정합니다. 아래는 전부 실제 영화 자막으로 재어 가며 정한 것입니다.

```
그림 ─ 검은 바탕에 합성 ─ 흑백 반전 ─ 기울기 바로 세우기
                                        │
     줄마다 자르기 ─ 음표(♪) 찾아 떼기 ─ 크기 맞추기 ─ 인식기
```

### 1. 기울어진 글자 바로 세우기

처음 실제 영화를 넣었을 때 인식이 무너진 곳은 **기울어진 노래 가사**였습니다.
자막 글꼴이 기울면 인식기가 거의 못 읽습니다. 합성 자료로는 밟아 볼 수 없던
부분이라, 실제 자막을 넣고서야 드러났습니다.

바로 선 글자는 세로획이 같은 열에 모입니다. 그래서 열마다 잉크량을 재면 획이
있는 열과 없는 열의 차이가 큽니다. 여러 기울기로 되돌려 보고 그 차이가 가장 큰
것을 고릅니다.

| 자막 | 전 | 후 |
|---|---|---|
| 노래 가사 215줄 (기울어짐) | 한글 31.6% | **92.8%** |
| 대사 220줄 (똑바름) | 한글 97.3% | 97.3% (그대로) |

똑바른 글자는 기울기가 0으로 나오므로 **아무것도 건드리지 않습니다.**

```
전: .?/7/.</으 흔 을을 ////./들 / 준//_.7 8/./?7
후: 마지막 한 발을 내디딜 / 준비가 됐니?
```

### 2. 글자는 클수록 좋은 게 아닙니다

그 다음 남은 것이 **ㅈ 을 ㅅ 으로 읽는 실수**였습니다(`자네가`→`사네가`,
`저런`→`서런`). 그림을 열어 보면 `자` 가 또렷한데도 그랬습니다. 그래서 전처리가
아니라 **넣는 크기**를 의심했습니다. 원본 크기를 바꿔 가며(한 줄 25~100픽셀)
재 보니 분명했습니다.

| 인식기에 넣는 크기 | 글자정확도(최저) | ㅈ↔ㅅ 실수(최다) |
|---|---|---|
| 2배로 키움 (예전 기본값) | 92.10% | **14** |
| 손대지 않음 | 93.79% | 8 |
| **28픽셀로 줄임** | **96.61%** | **0** |

**키우는 것은 어느 크기에서도 손해였습니다.** 예전 기본값이 2배 확대였으니,
설정을 올릴수록 나빠지고 있었던 셈입니다. 그래서 큰 글자만 줄이고 키우지는
않습니다. 한 줄이 40픽셀보다 작으면 줄여도 나아지지 않으므로 그냥 둡니다.

> 원인을 헛짚지 않으려고 따로 확인했습니다. 흐리게만 해도(ㅈ↔ㅅ 8~10),
> 줄였다 다시 키워도(2~6) 듣지 않았습니다. **작게 넣는 것 자체**가 듣는
> 방법이었습니다. Tesseract 설정(psm, 사전 관련 값)은 어느 것도 효과가 없었습니다.

덤으로 그림이 작아져 인식이 **두 배 가까이 빨라졌습니다.**

### 3. 줄마다 따로 읽습니다

자막 한 덩이를 통째로 넣으면 인식기가 줄 배치를 제 나름대로 해석합니다. 자막은
가운데 맞춤이라 줄마다 여백이 다른데, 그 여백을 글자로 오해해 앞에 `.` 이나 `_`
를 만들어 내고 때로는 **한 줄을 통째로 흘립니다.**

```
전: . 그런 말투는 / 누구한테 배웠나?     ← 없는 점이 생김
전: 평크에                            ← '팝이' 가 통째로 사라짐
```

그래서 글자 줄마다 잘라 따로 넣습니다. 잘라 낼 때는 위아래에 줄 높이의 15%를
남깁니다. 딱 붙여 자르면 인식기가 글자의 기준선을 못 잡고(실측: `English` →
`Enalish`), 25%를 넘기면 옆 줄이 딸려 들어옵니다.

**빈 결과가 나오면 '한 낱말' 모드로 한 번 더 읽습니다.** '한 줄' 모드는 줄을 아예
못 찾으면 아무것도 내놓지 않는데, 그러면 그 자막이 빈 채로 걸러져 **통째로
사라집니다.** 블루레이 자막에서 `잠깐...` 한 줄이 그렇게 없어진 것을 폰과 PC 의
자막 수가 갈리면서(1,593 대 1,592) 발견했습니다.

빈 결과일 때만 발동하므로 없던 글자를 만들지 않고, 다시 읽어도 빈 값이면 그대로
둡니다. 실측으로 자막 세 편 7,084줄 중 **3줄**에서만 발동했고 세 줄 다 살아났습니다.

| 그림 | 다시 읽은 결과 |
|---|---|
| `- 난 그냥…` | `- 난 그냥…` ✅ |
| `뭐…` | `뭔…` (받침이 하나 붙음) |
| `잠깐...` | `잠깐.…` (마침표가 하나 남음) |

셋 중 둘은 글자 하나가 어긋납니다. 그래도 **자막이 통째로 없어지는 것보다는
낫다**고 보고 그대로 씁니다 — 글자 하나는 고쳐 읽을 수 있지만 없는 자막은
사용자가 있었는지도 모릅니다.

### 4. 줄 높이는 트랙 전체에서 잽니다

`응` 이나 `요즘` 처럼 위아래로 쌓인 글자는 **가운데가 가로로 비어 있습니다.**
긴 줄에서는 옆 글자들이 그 자리를 메우지만, 글자 몇 자뿐인 짧은 줄에서는 그대로
끊깁니다. 그러면 한 줄이 두 줄로 갈려 엉뚱하게 읽힙니다.

```
전: - 왔어? / "> / 222      ← '- 응' 이 두 조각으로 끊김
후: - 왔어? / - 응
```

조각 사이 틈(12픽셀)이 줄 사이 틈(11픽셀)과 거의 같아 **틈 크기만으로는 가릴 수
없습니다.** 대신 자막은 한 트랙 안에서 글자 크기가 일정하다는 점을 씁니다. 여러
자막에서 재어 가운데 값을 쓰면 아주 안정적입니다(실측: 영화 A 는 자막 1,578개에서
중앙값 49픽셀·사분위 48~49픽셀, 영화 B 는 48픽셀). 글꼴이 달라도 한 트랙 안에서는
거의 흔들리지 않습니다.

그 값으로 '합쳐도 한 줄 높이를 넘지 않으면 같은 줄' 로 붙이고, 너무 얇게 잡힌
띠는 글자가 잘린 것으로 보고 한 줄 크기로 넓힙니다. 쓰레기 줄이 **11줄 → 0줄**
이 됐습니다.

### 5. 음표(♪)는 그림에서 찾아냅니다

노래 자막의 ♪ 는 **인식기가 절대 못 읽습니다.** 한국어·영어 글자 목록(1158자 /
112자)에 ♪ 가 아예 없기 때문입니다. 실제로 영화 한 편에서 한 번도 못 읽었고,
대신 `》` `^` `_` `>` 같은 엉뚱한 글자를 내거나 그냥 흘렸습니다.

글자로는 고칠 수 없으니 **그림에서 직접 찾습니다.** 줄 맨 앞 덩어리를 ♪ 본과
견줍니다. 실측으로 두 무리가 확실히 갈립니다.

| | 본과 닮은 정도 |
|---|---|
| **음표** | 0.49 ~ 0.74 |
| 한글 | -0.14 ~ 0.27 |
| 대시(`-`) | -0.09 ~ -0.03 |

기울기·폭·아래쏠림 같은 생김새 값만으로는 **하나도 갈리지 않았습니다**(좁은
한글 `이`·`니`·`리` 와 겹칩니다). 본과 견주는 방법만 깨끗하게 갈렸습니다.

찾으면 그림에서 지우고(안 지우면 인식기가 그 자리에 엉뚱한 글자를 만듭니다)
결과 앞에 ♪ 를 붙입니다. 영화 한 편에서 **231곳**을 되살렸습니다.

> '줄 앞에 이상한 글자가 있으면 음표' 로 고칠 생각이었는데, 12개를 눈으로
> 확인해 보니 **절반만 진짜 음표**였습니다. 글자만 보고 고쳤으면 없는 음표를
> 만들어 낼 뻔했습니다.

두 번째 영화가 이 선택을 확인해 줬습니다. 그 영화는 노래를 음표가 아니라
**기울임꼴로만** 표시합니다(자막의 36%가 기울임꼴, ♪ 글리프 0개). 그림에서 찾는
지금 방식은 **0곳**을 보고했고 그것이 정답이었습니다. 글자를 보고 고치는 방식이면
없는 음표를 수백 개 만들어 냈을 자막입니다.

### 6. 인식 언어는 자동으로 고릅니다

| 인식 언어 | 한글만 있는 자막 | 한·영 섞인 자막 |
|---|---|---|
| 한국어만 | **98.0%** | 39% ❌ 영문이 깨집니다 |
| 한국어 + 영어 | 89.7% | **100%** |

어느 한쪽이 항상 낫지 않습니다. 그래서 앞부분 12장을 '한국어+영어'로 읽어 보고
두 가지를 **함께** 봅니다 — 영문 낱말을 인식기가 얼마나 확신하는지(50 이상),
그리고 낱말 가운데 영문이 얼마나 되는지(20% 이상). 둘 다 맞아야 영어를 씁니다.

파이썬판도 같은 규칙을 씁니다(`subex.ocr.pick_language`). 같은 입력에 같은 답을
내야 두 판의 결과가 갈리지 않으므로, 판단 함수만 따로 떼어 **양쪽에 값까지 똑같은
시험**을 두었습니다.

| 자료 | 영문 낱말 비율 | 확신도 | 고른 언어 |
|---|---|---|---|
| 한글 전용 (합성 자료) | 0.0% | — | 한국어만 |
| 한글 전용 (실제 DVD 자막, 영화 A) | 5.7% | 54.8 | 한국어만 |
| 한글 전용 (실제 DVD 자막, 영화 B) | 3.9% | 15.0 | 한국어만 |
| 한·영 혼합 (합성 자료) | 53.8% | 95.4 | 한국어+영어 |

한글 전용 자막을 '한국어+영어'로 읽으면 멀쩡한 한글이 영문으로 뭉개지지만
(실측: 300줄 중 83줄, 28%), 영문이 조금 섞인 자막을 '한국어만'으로 읽으면 그 몇
낱말만 깨집니다. 그래서 **영문이 진짜로 섞여 있다는 증거가 뚜렷할 때만** 영어를
함께 씁니다.

> 처음에는 두 설정의 전체 신뢰도를 견주려 했는데, 400장에서 89.8 대 89.5 로
> 뒤집혀 못 쓸 방법이었습니다. 확신도만 보도록 바꾸니 89.7% → 98.0% 가 됐지만,
> 실제 DVD 자막에서 기울어진 가사가 영문으로 잘못 읽히며 확신도가 54.8 로
> 어중간하게 높게 나와 또 틀렸습니다. 그래서 비율을 함께 보게 했습니다.

### 7. 마무리 손질

대화 표시(`-`) 뒤 띄어쓰기를 되살립니다. 인식기가 가끔 흘리는데 그림에는
띄어쓰기가 있기 때문입니다. 다만 **무조건 띄우면 안 됩니다.** 자막마다 관습이
다릅니다.

| | 대시로 시작하는 줄 | 그중 띄어쓴 것 |
|---|---|---|
| 영화 A | 184줄 | 179줄 (97%) |
| 영화 B | 49줄 | **0줄 (0%)** |

처음에는 표본이 한 편뿐이라 '`-` 로 시작하면 무조건 띄운다' 로 굳혔는데, 두 번째
영화를 넣어 보니 그 규칙이 멀쩡한 49줄을 원본과 다르게 만들고 있었습니다.

그래서 줄 하나가 아니라 **트랙 전체**를 먼저 셉니다. 띄어쓴 줄이 70% 를 넘으면
'띄어쓰는 자막' 으로 보고 붙어 있는 소수를 맞추고, 그렇지 않으면 손대지 않습니다.
띄어쓰기를 **없애지는 않습니다** — 인식기가 없는 띄어쓰기를 만들어 내는 일은
드뭅니다. 음수(`-5도`)는 어느 쪽이든 건드리지 않습니다.

그 밖에 빈 줄을 없애고, 겹치는 시각을 정리하고, 같은 글자가 이어지면 한 덩어리로
합칩니다.

## 어떻게 검증했나

이 저장소의 **파이썬판이 정답지**입니다. 실제 영상으로 검증을 끝낸 구현이라,
웹판이 같은 입력에서 같은 답을 내는지를 기준으로 삼았습니다.

```bash
npm test
```

52개 시험이 있고, 대부분 **파이썬판이 낸 답과 맞춰 봅니다**.

| 시험 | 내용 |
|---|---|
| SRT 규칙 대조 | 까다로운 11가지 경우에서 파이썬판과 글자 단위로 같은지 |
| PGS 그림 해독 | 파이썬판이 해독한 그림과 **픽셀 단위로** 같은지 (.sup 파일 / MKV 안 둘 다) |
| VobSub 그림 해독 | 위와 같음 |
| .idx/.sub 짝 | 영상 없이 자막 파일 두 개만 넣어도 픽셀 단위로 같은지, .idx 표를 언어별로 갈라 읽는지, **하나씩 차례로 골라도**(양쪽 순서 모두) 이어지는지 |
| MKV 글자 자막 | SubRip 이 그대로 읽히는지 |
| MP4 자막 트랙 | 트랙·언어를 찾아내고, SRT 와 시각이 파이썬판과 **밀리초까지** 같은지 |
| 파일 종류 가리기 | 앞머리만 보고 MKV·MP4·.sup 을 구분하고, 모르는 형식은 이유를 알려 주는지 |
| 자막 없는 영상 | 빈 목록과 안내 문구가 나오는지 |
| 실제 자막에 가까운 PGS | 안티에일리어싱(수십 가지 색)과 두 줄을 각각 다른 객체로 얹은 경우도 픽셀 단위로 같은지 |
| 기울기 바로 세우기 | 기울기를 제대로 재는지, 되돌린 뒤 0이 되는지, 똑바른 그림은 손대지 않는지 |
| 글자 크기 맞춤 | 줄 높이를 제대로 재는지, 큰 글자만 줄이고 작은 글자는 그대로 두는지 |
| 줄 가르기·음표 | 줄 수만큼 갈리는지, **글꼴이 그린 진짜 ♪** 를 찾아 떼어 내는지, 글자를 음표로 잘못 보지 않는지 |
| 트랙 줄 높이 | 가운데가 빈 짧은 줄을 도로 붙이는지, 진짜 두 줄은 붙이지 않는지, 조각난 그림이 섞여도 흔들리지 않는지 |
| 자동 언어 선택 | 한글 전용에서는 '한국어만', 한·영 혼합에서는 '한국어+영어'를 고르는지 |
| 대화 표시 띄어쓰기 | `-응` → `- 응` 으로 되살리되 음수는 건드리지 않는지 |
| zip 묶기 | CRC-32 가 규격 값과 같은지, 1980년 이전 날짜도 담기는지, 이름 없는 항목은 알려 주는지, **파이썬 `zipfile` 이 우리 zip 을 그대로 읽는지**(한글 이름·빈 파일 포함) |
| 고르고 받는 화면 | 자막 8개짜리 영상에서 스스로 고르지 않는지, 전체 선택·해제와 언어별 고르기가 듣는지, 셋만 골라 받으면 **그 셋만 든 zip** 이 받아지는지 |
| 따라다니는 실행 막대 | 목록 맨 위·가운데 어디서든 추출 단추가 화면 안에 있는지, 맨 아래에서 마지막 트랙을 가리지 않는지, 돌아가는 동안 단추에 진행이 적히고 끝나면 진행선이 사라지는지, 끝난 뒤 결과 막대가 눈앞에 오는지 |
| 연 파일 이름 | 트랙을 다 찾은 뒤에도 파일 이름과 크기가 화면에 남는지, DVD 자막은 `.idx`/`.sub` 두 이름을 다 적는지 |
| 미리보기 시각 | 자막마다 시작 시각이 앞에 붙는지, 파일 안의 값과 같은지, 두 줄짜리 자막이 한 덩어리로 남는지 |
| **브라우저 전체 흐름** | 진짜 크로미움에서 MKV·MP4·.sup·.idx+.sub 을 넣고 끝까지 돌려, 만들어진 SRT 가 파이썬판 결과와 **바이트 단위로 같은지** |

마지막 시험이 핵심입니다. 자막을 꺼내고, 그림을 해독하고, 글자를 읽고, 다듬어
SRT 로 만드는 전 과정을 한 번에 확인합니다.

### 실제 영화 자막에서의 대조 결과

같은 영화 자막을 양쪽으로 돌려 맞춰 본 값입니다.

| | 영화 A (DVD) | 영화 B (DVD) | 영화 C (블루레이) |
|---|---|---|---|
| 자막 수 | 1,578 / 1,578 — **같음** | 1,661 / 1,661 — **같음** | 1,593 / 1,593 — **같음** |
| 시각 | **완전히 같음** | **완전히 같음** | **완전히 같음** |
| 그림 해독 | **픽셀 하나까지 같음** (605만 픽셀, 차이 0) | — | — |
| 글자 | **99.91%** 일치 | **99.87%** 일치 | **99.88%** 일치 |

> 영화 C 를 넣고서야 **양쪽 시각이 어긋나는 결함 두 가지**가 드러났습니다.
> 파이썬판이 `.sup` 을 ffmpeg 으로 다시 써서 읽는 바람에 자막 전체가 53.072초
> 빨라졌고, 90kHz 눈금을 밀리초로 바꿀 때 한쪽은 버리고 한쪽은 반올림해서
> 1,592줄 중 794줄이 1밀리초씩 갈렸습니다. 둘 다 고쳤고 회귀 시험을 붙였습니다.
> DVD 자막은 차례표에 시각이 이미 밀리초로 적혀 있어 두 결함이 보이지 않았습니다.

파이썬판은 ffprobe 로 읽고 웹판은 프로그램 스트림을 직접 훑습니다. 서로 다른
길로 같은 답에 닿은 셈입니다. 남은 0.1% 안팎은 인식 엔진이 서로 달라(WebAssembly
대 네이티브) 생기는 차이이고, 웹판이 더 잘 읽은 곳도 섞여 있습니다
(`실어`→`싫어`, `♪년 홀로`→`♪넌 홀로`).

### 실제 영상으로 직접 검증하기

가진 영상을 넣으면 웹판을 돌려 보고, 이 컴퓨터에 파이썬판이 있으면 **자동으로
대조까지** 해 줍니다.

```bash
node tools/verify.js /경로/영화.mkv            # 웹판 실행 + 파이썬판 대조
node tools/verify.js 영화.mkv --dump 5         # 해독한 그림도 5장 저장해 눈으로 확인
node tools/verify.js 영화.mkv --lang kor       # 인식 언어를 직접 지정
node tools/verify.js 영화.mkv --no-python      # 대조 없이 웹판만
node tools/verify.js 자막.idx 자막.sub         # DVD 자막은 두 파일을 함께
```

내놓는 것: 트랙 목록, 단계별 걸린 시간, SRT 파일, 그리고 파이썬판과의 **시각
일치 여부**와 **글자 일치율**, 다른 곳 다섯 군데까지. 대조할 때는 **양쪽이 같은
인식 언어**를 쓰도록 맞춥니다(안 맞추면 해독이 멀쩡한데도 다르다고 나옵니다).

시각이 다르면 자막을 꺼내는 쪽 문제이고, 글자만 다르면 문자 인식 차이입니다.
`--dump` 로 저장되는 그림을 보면 인식기가 무엇을 보고 읽었는지 알 수 있습니다.

기준 자료를 다시 만들려면:

```bash
python3 ../tests/make_web_fixtures.py     # 그림·영상·SRT 정답지
python3 ../tests/make_parity_golden.py    # SRT 규칙 정답지
```

## 직접 띄우기

```bash
cd web
npm install && npm run vendor   # 문자 인식 엔진을 vendor/ 로 복사 (한 번만)
npm run serve                   # http://127.0.0.1:8080
```

이 저장소에 올릴 때마다 `.github/workflows/pages.yml` 이 자동으로 다시 배포합니다.
올릴 때 문자 인식 엔진과 언어 자료를 함께 담으므로, 공개 배포망에 기대지 않고
사이트 혼자 돌아갑니다.

직접 배포하실 때도 이 폴더를 정적 파일 그대로 올리면 끝입니다(사내 웹서버, 파일
공유 등). **서버에서 도는 프로그램이 없습니다.** `npm run vendor` 를 하면 인식
엔진과 언어 자료가 `vendor/` 에 들어가 **바깥 인터넷이 막힌 사내망에서도** 그대로
동작합니다. 하지 않으면 공개 배포망에서 받아 옵니다.

## 구조

```
web/
├── index.html · styles.css        화면 (반응형, 360픽셀부터)
├── src/
│   ├── reader.js       파일을 조각내어 읽기 (필요한 구간만)
│   ├── container.js    파일 종류를 가려 알맞은 해석기로
│   ├── mime.js         자막 형식 이름표 (해석기와 뽑기가 같이 쓴다)
│   ├── mkv.js          MKV/WebM 해석 — 자막 트랙만 골라 꺼낸다
│   ├── mp4.js          MP4/MOV 해석 — 표(stbl)를 엮어 자막 조각 위치를 찾는다
│   ├── pgs.js          PGS 그림 해독 (세그먼트 + 런렝스)
│   ├── vobsub.js       VobSub 그림 해독 (제어 시퀀스 + 2비트 런렝스)
│   ├── vobsubFile.js   .idx 표 읽기 + .sub(MPEG 프로그램 스트림)에서 자막 꺼내기
│   ├── source.js       고른 파일들을 정리 (.idx/.sub 을 하나씩 받아 모은다)
│   ├── extract.js      위를 엮어 '시각 + 내용' 으로
│   ├── bitmapPrep.js   인식 전처리 (기울기·크기 맞추기, 줄 가르기, 음표 찾기)
│   ├── ocr.js          문자 인식 (tesseract.js, 여러 개 병렬, 언어 자동 선택)
│   ├── postprocess.js  다듬기 (대화 표시 띄어쓰기·빈 줄·겹침·중복)
│   ├── srt.js          SRT 읽기/쓰기
│   ├── zip.js          결과 여러 개를 zip 하나로 묶기 (압축 없이 저장)
│   ├── config.js       인식 엔진 불러오기 (vendor/ → 공개 배포망 순)
│   └── app.js          화면 동작
├── tools/              개발 서버, 인식 엔진 복사, 실제 영상 검증(verify.js)
└── test/               위 검증들
```

## 아직 안 된 것

- **조각난 MP4(fragmented)** — 스트리밍용으로 만든 MP4 입니다. 읽으려 하면
  그렇다고 알려 줍니다.
- **DVB 자막(방송)** — 목록에는 보이지만 해독기가 없습니다.
- **화면에 새겨진 자막(번인)** — 자막 트랙이 아니라 영상 그림의 일부라 범위 밖입니다.
- 문자 인식은 한국어+영어로 맞춰 두었습니다. 다른 언어는 `vendor.js` 의 언어
  목록과 `ocr.js` 의 기본값을 바꾸면 됩니다. 음표(♪) 찾기와 기울기 바로 세우기는
  언어와 무관하게 그대로 듣습니다.
